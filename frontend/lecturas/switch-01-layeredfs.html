SWITCH

Estructura de capas de archivos

En Switch desaparece la necesidad de reempaquetar el juego para modificarlo. El sistema intercepta las lecturas de archivos y entrega una version externa cuando existe, lo que cambia por completo el flujo de trabajo respecto a GBA y DS.

1. Sustituir sin reescribir

Las tecnicas de GBA y DS comparten una premisa: para cambiar algo hay que modificar la imagen del juego y volver a empaquetarla. En Switch esa premisa desaparece. El sistema intercepta las lecturas de archivos y, si existe un archivo con la misma ruta en una carpeta externa, entrega ese en lugar del original.

El juego instalado nunca se toca. Sigue en su formato firmado, intacto, y lo que se distribuye es una carpeta con los archivos sustituidos. Las ventajas son inmediatas: un cambio de textura pesa lo que pesa la textura, se prueba reiniciando el juego, y desactivar una modificacion consiste en renombrar una carpeta.

La regla de la ruta exacta

La superposicion se decide comparando rutas. Si el juego abre /Data/Model/player.bfres y tu archivo esta en /data/model/player.bfres, no se sustituye nada. Mayusculas, guiones y extensiones deben coincidir caracter a caracter con lo que hay en el RomFS original.

2. El Title ID

Cada juego se identifica con un numero de 64 bits que se escribe como 16 digitos hexadecimales. Es la clave que enlaza tu carpeta de modificaciones con el juego correcto, y hay que tener presente que las actualizaciones y los contenidos descargables tienen identificadores derivados pero distintos del programa base.

Tipos de contenido y su identificador
Contenido Relacion con el ID base Donde se modifica
Programa base El ID tal cual, terminado en 000 Carpeta del ID base
Actualizacion Mismo ID con los ultimos digitos a 800 Carpeta del ID base
Contenido descargable ID con el bloque final incrementado Carpeta propia del DLC

La confusion habitual es esperar que una modificacion aplicada al programa base afecte a archivos que en realidad llegaron con una actualizacion. Cuando una actualizacion reemplaza un archivo, es su version la que el juego abre, y es esa ruta la que hay que superponer.

3. Estructura de carpetas

El diseno es deliberadamente literal: dentro de la carpeta del juego, una subcarpeta romfs que reproduce el arbol de recursos y una exefs para el codigo ejecutable.

tarjeta SDARBOL
sd:/
 └── atmosphere/
     └── contents/
         └── 0100ABCDEF123000/      ; Title ID del juego
             ├── romfs/
             │   ├── Data/
             │   │   └── Model/
             │   │       └── player.bfres
             │   └── Message/
             │       └── es.msbt
             ├── exefs/
             │   └── main.npdm
             └── cheats/
                 └── A1B2C3D4E5F60718.txt

Solo hay que incluir los archivos que se sustituyen. No se copia el RomFS completo: la carpeta contiene exclusivamente las rutas modificadas, y todo lo demas se sirve del juego original.

4. Que ocurre al abrir un archivo

El proceso que intercepta las llamadas al sistema de archivos comprueba, para cada apertura, si existe una version superpuesta. La logica es de todo o nada por archivo:

  1. El juego solicita una ruta dentro de su RomFS.
  2. La capa de interceptacion busca esa ruta bajo la carpeta del Title ID.
  3. Si existe, devuelve el archivo externo. Si no, deja pasar la peticion al original.
No hay mezcla parcial

La sustitucion opera sobre archivos completos, no sobre su contenido. Si un archivo empaquetado contiene cien texturas y quieres cambiar una, tienes que extraer el paquete, cambiar la textura, reconstruir el paquete entero y superponer el resultado. La capa de archivos no sabe nada de lo que hay dentro.

5. Varias modificaciones a la vez

Aqui esta el limite real del sistema. Dos modificaciones que sustituyan archivos distintos conviven sin problema, pero dos que sustituyan el mismo archivo son incompatibles: solo una carpeta puede ganar, y la otra queda ignorada por completo.

El caso mas frecuente es el de los archivos de parametros globales, que suelen ser uno solo para todo el juego. Cualquier modificacion que ajuste valores de equilibrio tocara ese archivo, y por eso dos de ellas casi nunca se pueden combinar sin fusionarlas a mano.

Diagnostico cuando una modificacion no se aplica
  1. Title ID. Verificalo contra el que informa el propio sistema, no contra una lista de internet. Un digito distinto y la carpeta se ignora en silencio.
  2. Ruta interna. Extrae el RomFS original y compara la ruta completa, incluidas mayusculas. Es el fallo mas comun con diferencia.
  3. Carpeta de mas. Un nivel extra al descomprimir el archivo distribuido deja la estructura desplazada. Debe haber una carpeta romfs directamente bajo el Title ID.
  4. Actualizacion instalada. Si el archivo lo aporta una actualizacion, la ruta puede haber cambiado respecto al juego base.
  5. Conflicto. Desactiva el resto de modificaciones y prueba la tuya sola.

Si tras estos cinco pasos sigue sin funcionar, comprueba que el propio archivo es valido reemplazandolo temporalmente por una copia del original. Si asi tampoco arranca, el problema esta en la estructura de carpetas y no en el contenido.

6. Coste de rendimiento

Cada apertura de archivo pasa por una comprobacion adicional en la tarjeta SD, que es mucho mas lenta que la memoria interna. Con unos pocos archivos superpuestos el efecto es imperceptible, pero una modificacion que sustituya miles de rutas puede alargar visiblemente los tiempos de carga.

La contramedida es agrupar. Un unico archivo empaquetado grande se abre una vez; mil archivos sueltos se abren mil veces. Cuando una modificacion crece, reempaquetar los recursos en los contenedores originales del juego suele recuperar el rendimiento perdido.
