Parches de codigo IPS

La superposicion de archivos resuelve los recursos, pero no el comportamiento. Cambiar la logica de un juego exige parchear su codigo en memoria, y este documento explica el formato empleado, como se calculan los offsets y por que el Build ID evita desastres.

1. Recursos y codigo son cosas distintas

La superposicion de archivos resuelve todo lo que sea un recurso: texturas, textos, modelos, tablas de datos. Lo que no puede tocar es el comportamiento. Si quieres que una comprobacion deje de ejecutarse o que una constante interna valga otra cosa, hay que modificar el codigo del programa, y eso vive en otra capa.

El codigo se distribuye en modulos ejecutables que el sistema carga al arrancar el juego. Un parche de codigo es una lista de sustituciones de bytes que se aplican a ese modulo despues de cargarlo en memoria y antes de que empiece a ejecutarse. El archivo instalado no se altera nunca.

2. El Build ID

Cada compilacion de cada modulo lleva un identificador unico generado al compilar. Es la pieza que impide desastres: un parche escrito para una version del juego tiene un Build ID que no coincide con el de otra version, asi que sencillamente no se aplica.

Por que esto es una buena noticia

Un parche de codigo escribe bytes en offsets fijos. Si se aplicara a una version distinta, esos offsets caerian en instrucciones diferentes y el resultado seria un cuelgue impredecible. Emparejar por Build ID convierte un fallo silencioso y peligroso en un parche que simplemente no hace nada.

De ahi la convencion de nombrar el archivo de parche con el Build ID del modulo al que va dirigido. El sistema recorre la carpeta de parches, compara el nombre con el identificador del modulo que acaba de cargar y aplica solo lo que coincide. Es tambien el motivo por el que un parche deja de funcionar tras actualizar el juego: la actualizacion recompila el modulo y cambia su identificador.

3. El formato IPS

IPS es un formato de parcheo antiguo, anterior a todo esto, que se reutiliza aqui por su simplicidad. Un parche IPS es una secuencia de registros donde cada uno dice: en esta posicion, escribe estos bytes.

formato IPS clasicoESTRUCTURA
+--------------------------------------------+
| "PATCH"   5 bytes ASCII                  |
+--------------------------------------------+
| registro:                                  |
|   offset    3 bytes  BIG-endian            |
|   tamano    2 bytes  BIG-endian            |
|   datos     N bytes                        |
+--------------------------------------------+
| ... mas registros ...                      |
+--------------------------------------------+
| "EOF"     3 bytes ASCII                  |
+--------------------------------------------+
Big-endian

Los offsets y tamanos de IPS van en big-endian, al reves que todo lo demas en estas plataformas. Un offset 0x001A40 se escribe 00 1A 40, no 40 1A 00. Es el error mas repetido al generar parches con un script propio.

La limitacion evidente del formato clasico es que tres bytes de offset solo alcanzan a direccionar 16 MiB, insuficiente para modulos modernos. Por eso circula una variante extendida con offsets de cuatro bytes, identificada por una firma distinta, que es la que se usa en la practica.

Variantes del formato
Variante Firma Offset Alcance
IPS clasico PATCH / EOF 3 bytes 16 MiB
IPS extendido IPS32 / EEOF 4 bytes 4 GiB

4. Del desensamblado al offset del parche

El desensamblador muestra direcciones de memoria virtual, no offsets dentro del archivo del modulo. Entre ambos hay una diferencia constante: la direccion base donde se carga el modulo, mas el desplazamiento de la seccion de codigo dentro de el.

conversionARITMETICA
; Lo que ve el desensamblador
direccion virtual   = 0x00812A40

; Base de carga del modulo en el analisis
base                = 0x00800000

; Offset dentro del modulo
offset = direccion - base = 0x00012A40

; Ese es el numero que va en el registro IPS

Equivocarse en la base produce un parche que escribe en un sitio arbitrario. El sintoma es un cuelgue inmediato al arrancar, y la comprobacion es directa: lee los bytes originales en ese offset del modulo extraido y confirma que coinciden con la instruccion que pretendias sustituir. Si no coinciden, la base esta mal.

5. Sustituciones habituales en ARM64

La mayoria de los parches de codigo son cambios minusculos. Estas son las tres operaciones que cubren casi todos los casos:

Patrones frecuentes
Objetivo Tecnica Efecto
Anular una comprobacion Sustituir el salto condicional por NOP La ejecucion continua siempre
Forzar un valor de retorno Cargar la constante en el registro de retorno y volver La funcion devuelve siempre lo mismo
Cambiar una constante Reescribir el inmediato de la instruccion Ajusta un limite o un multiplicador

Las instrucciones ARM64 miden cuatro bytes exactos, lo que simplifica mucho el trabajo: toda sustitucion ocupa lo mismo que lo sustituido y no hay que reubicar nada. Recuerda que los bytes se escriben en little-endian, asi que una instruccion que el desensamblador muestra como D503201F aparece en el volcado como 1F 20 03 D5.

6. Trucos en tiempo real

Existe una via alternativa que no toca el codigo sino la memoria mientras el juego corre. Un archivo de trucos declara escrituras periodicas sobre direcciones de RAM, condicionadas a que se pulse una combinacion de botones o a que un valor cumpla cierta condicion.

Parche de codigo frente a truco de memoria
Aspecto Parche de codigo Truco de memoria
Momento Una vez, al cargar Continuamente, en ejecucion
Alcance Cambia la logica Cambia valores
Activacion Siempre activo Se puede alternar
Coste Ninguno tras cargar Comprobaciones por fotograma
Riesgo Cuelgue al arrancar si falla Corrupcion de partida si escribe mal
Cual elegir para cada situacion

Si lo que quieres es alterar un valor que el jugador ve y que el juego recalcula constantemente, el truco de memoria es la herramienta adecuada: se activa y se desactiva, y no compromete el arranque.

Si lo que quieres es que el juego se comporte de otra manera de forma permanente, el parche de codigo es la unica via. Un truco que escriba un valor sesenta veces por segundo no puede reemplazar a un cambio en la logica, y ademas compite con el propio juego por ese dato.

El peor escenario es usar un truco para forzar un valor que despues se guarda en la partida. Ahi el efecto sobrevive al truco: has escrito en el archivo de guardado un estado que el juego no considera valido, y el problema aparecera mucho despues de haber desactivado el truco.

Ambos comparten la dependencia de la version. Los trucos apuntan a direcciones de memoria que cambian entre compilaciones exactamente igual que los offsets de codigo, y por eso tambien se organizan por Build ID.

7. Prudencia

Los parches de codigo se aplican antes de que el juego ejecute su primera instruccion, asi que un error no da segundas oportunidades: la consola se queda colgada y hay que reiniciarla. Trabaja con un parche cada vez, prueba tras cada cambio y anota que hace cada registro. Un archivo IPS de veinte registros sin documentar es imposible de depurar seis meses despues.

Y guarda siempre los bytes originales que sustituyes. Es lo que te permite verificar que apuntabas al sitio correcto y revertir un cambio concreto sin rehacer el parche entero.
