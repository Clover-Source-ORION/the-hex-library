Cabecera del cartucho

Los primeros 192 bytes de un cartucho de Game Boy Advance no contienen código del juego, sino una ficha de identidad que la BIOS valida antes de ceder el control. Conocerla permite verificar un volcado, identificar su versión exacta y diagnosticar por qué una ROM deja de arrancar.

1. Qué hace la cabecera

Los primeros 192 bytes (0x000 a 0x0BF) de todo cartucho de Game Boy Advance son leídos por la BIOS antes de ejecutar el programa. Si la información no coincide con las firmas esperadas o falla la verificación, la consola se bloquea en la pantalla del logotipo de Nintendo y no ejecuta una sola instrucción del juego.

Para el ROM hacking y el análisis técnico, esta región es fundamental por dos motivos principales:

  • Integridad en el arranque: Cualquier herramienta que reescriba datos en este rango debe mantener la estructura o recalcular la suma de comprobación; de lo contrario, el archivo quedará inoperativo.
  • Identificación unívoca: El código de juego de 4 letras sirve como identificador estándar que usan emuladores, parches IPS/UPS y bases de datos para reconocer la versión y región del juego.

3. Los 156 bytes intocables

El bloque comprendido entre 0x004 y 0x09F alberga los datos gráficos del logotipo de Nintendo. Durante la secuencia de inicio, la BIOS copia este bloque a la VRAM para dibujarlo en pantalla y lo compara directamente contra una copia almacenada en la ROM interna de la propia consola.

Protección por hardware

Modificar un solo bit de este bloque provocará que la consola real se bloquee en el arranque. Aunque ciertos emuladores omiten esta comprobación por conveniencia, alterar este espacio impedirá siempre la ejecución en hardware real.

4. Anatomía del código de juego

Ubicado en el offset 0x0AC, este campo consta de cuatro caracteres ASCII cuya estructura revela información clave sobre la ROM:

gamecode.txtASCII
            A X V E
            | |_| |
            |  |  +--- Región de destino
            |  |        E = América   P = Europa
            |  |        J = Japón     S = España
            |  |        F = Francia   D = Alemania
            |  |        I = Italia
            |  |
            |  +------ Identificador único del título (2 caracteres)
            |
            +--------- Tipo de soporte (A o B = Cartucho GBA estándar)

Compatibilidad de parches y versiones:
Dos volcados con el mismo ID corto pero distinta letra de región no comparten la misma disposición de memoria. Las traducciones y localizaciones modifican las tablas de texto, desplazando las direcciones de memoria (offsets). Aplicar un parche diseñado para la versión estadounidense (E) sobre una ROM europea (P) corrompe casi siempre los datos.

5. Cálculo del complemento de control

El byte situado en 0x0BD valida la integridad del rango 0x0A0 - 0x0BC (título, código de juego, fabricante, valor fijo y revisión). El algoritmo oficial se implementa de la siguiente manera:

checksum.cC
uint8_t checksum_cabecera(const uint8_t *rom)
{
    uint8_t chk = 0;

    // Suma acumulativa del rango 0xA0 a 0xBC (ambos incluidos)
    for (int i = 0xA0; i <= 0xBC; i++) {
        chk += rom[i];
    }

    // Aplicación del complemento con la constante fija 0x19
    return (uint8_t)(-(0x19 + chk));
}

La constante 0x19 es un parámetro fijo definido en las especificaciones del sistema. El resultado debe truncarse a un entero sin signo de 8 bits (uint8_t), o aplicar una máscara & 0xFF en lenguajes de alto nivel.

¿Cuándo es necesario recalcular el checksum?

Requieren recalculación: Modificaciones en el título interno (0x0A0), cambio del código de juego o actualización de la versión del software.

No afectan al checksum: Editar gráficos, reescribir tablas de datos, modificar código ensamblador o insertar scripts. Todo el contenido a partir del byte 0x0C0 queda fuera del ámbito de comprobación de la BIOS.

Nota: Este checksum valida exclusivamente la cabecera. No garantiza que la ROM esté completa ni que no existan errores en el resto del archivo.

6. Verificación de un volcado

Antes de manipular un archivo ejecutable, es aconsejable realizar tres comprobaciones de diagnóstico rápidas:

  • Comprobación de valor fijo: El byte en 0x0B2 debe contener exactamente 0x96. De lo contrario, el archivo no es un volcado válido de GBA.
  • Validación de Checksum: Calcula la suma de comprobación del rango 0x0A0 - 0x0BC y compara el resultado con el byte en 0x0BD. Un valor dispar indica modificaciones previas en la cabecera.
  • Dimensiones del archivo: El tamaño total debe corresponder a una potencia de dos exacta (4 MiB, 8 MiB, 16 MiB o 32 MiB). Tamaños irregulares suelen indicar datos extra insertados al final del archivo por herramientas de parcheado obsoletas.
Buena práctica

Conserva siempre un volcado original intacto (Clean ROM) verificado mediante sumas Hash (MD5/SHA-1). Distribuye tus modificaciones exclusivamente mediante archivos de parche (IPS, UPS o BPS) para garantizar el cumplimiento legal y evitar la distribución de material protegido.
