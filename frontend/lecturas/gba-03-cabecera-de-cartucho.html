Cabecera del cartucho

Los primeros 192 bytes de un cartucho de Game Boy Advance no son codigo del juego sino una ficha de identidad que el BIOS valida antes de ceder el control. Conocerla permite verificar un volcado, identificar su version y entender por que una ROM deja de arrancar.

1. Que hace la cabecera

Los primeros 192 bytes de todo cartucho de Game Boy Advance no son codigo del juego: son una ficha de identidad que el BIOS lee antes de ceder el control. Si algo ahi no cuadra, la consola se queda en la pantalla de arranque y no ejecuta una sola instruccion del programa.

Para el rom hacking esto importa por dos motivos. El primero es que cualquier herramienta que reescriba la ROM debe dejar la cabecera intacta o recalcularla. El segundo es que el codigo de juego de cuatro letras es el identificador que usan los parches, las bases de datos y los editores para saber que version tienen delante.

3. Los 156 bytes intocables

El bloque que va de 0x004 a 0x09F contiene el mapa de bits del logotipo de Nintendo comprimido, y el BIOS lo compara byte a byte contra su propia copia interna antes de arrancar. Un solo bit distinto y la consola se detiene.

No lo edites

Este bloque es una medida de control de licencias del hardware, no un espacio de datos. Modificarlo solo consigue que la ROM deje de arrancar en consola real, aunque algunos emuladores permisivos la sigan cargando y te den una falsa sensacion de que funciona.

4. Anatomia del codigo de juego

Los cuatro caracteres de 0x0AC siguen un esquema fijo. Leerlos correctamente te dice de que version es el volcado que tienes delante antes de abrir ningun editor:

gamecode.txtASCII
            A X V E
            | |_| |
            |  |  +--- Region
            |  |        E = America   P = Europa
            |  |        J = Japon     S = Espana
            |  |        F = Francia   D = Alemania
            |  |        I = Italia
            |  |
            |  +------ Identificador corto del titulo (2 chars)
            |
            +--------- Tipo de soporte: A o B = cartucho GBA

Dos volcados con el mismo identificador corto pero distinta region no son intercambiables. Los offsets de datos varian entre versiones localizadas porque las tablas de texto tienen tamanos distintos, y un parche compilado contra la version americana casi nunca cae en el sitio correcto de la europea.

5. Calculo del complemento de control

El byte de 0x0BD valida el tramo que va de 0x0A0 a 0x0BC, es decir, todo lo que hay entre el titulo y la version, ambos incluidos. El algoritmo cabe en cuatro lineas:

checksum.cC
uint8_t checksum_cabecera(const uint8_t *rom)
{
    uint8_t chk = 0;

    /* Suma de 0xA0 a 0xBC, ambos incluidos */
    for (int i = 0xA0; i <= 0xBC; i++)
        chk += rom[i];

    /* Complemento con la constante fija del formato */
    return (uint8_t)(-(0x19 + chk));
}

La constante 0x19 no se deduce de nada: forma parte de la especificacion. El truncado a 8 bits ocurre solo porque la variable es de un byte, asi que en lenguajes con enteros de tamano variable hay que aplicar una mascara & 0xFF explicita.

Cuando hay que recalcular el checksum y cuando no

Solo cuando toques algo entre 0x0A0 y 0x0BC. Los casos habituales son cambiar el titulo interno para distinguir tu build, o subir el byte de version.

Editar graficos, texto, mapas o codigo del juego no afecta a este byte: viven muy por encima de 0x0BF y el BIOS ni los mira. Si tu hack arranca sin problemas despues de mil ediciones y de pronto deja de hacerlo justo tras renombrar la ROM internamente, este byte es el primer sospechoso.

Ten en cuenta ademas que este checksum no tiene nada que ver con la integridad de los datos del juego. Que sea correcto no significa que el volcado este completo: solo significa que la ficha de identidad es coherente.

6. Verificacion de un volcado

Antes de empezar a trabajar sobre una ROM conviene confirmar que es lo que dice ser. Tres comprobaciones rapidas, en orden de coste:

  • Valor fijo. El byte de 0x0B2 debe ser 0x96. Si no lo es, ni siquiera estas ante una ROM de GBA.
  • Checksum. Recalcula el byte de 0x0BD y comparalo. Un desajuste indica una ROM ya intervenida.
  • Tamano. Debe ser potencia de dos, de 4 a 32 MiB. Un tamano irregular casi siempre significa que alguien anadio datos al final, que es precisamente donde suelen ir las inserciones de un hack previo.
Buena practica

Guarda una copia limpia y verificada antes de la primera edicion, y distribuye siempre tus cambios como parche en lugar de como ROM completa. Un parche pesa unos pocos KiB, deja claro sobre que version se aplica y no reparte material que no te pertenece.
