SWITCH

Ejecutables NSO y Build ID

Los programas de Nintendo Switch pueden distribuirse como módulos ejecutables NSO. Su cabecera describe segmentos de código y datos, y contiene un Build ID útil para identificar una compilación concreta. Esta guía explica cómo leer esa información sin confundir módulos, offsets del archivo y direcciones de memoria.

1. ¿Qué es un NSO?

Un NSO es un formato de módulo ejecutable usado en el entorno de Nintendo Switch. Un archivo NSO comienza con la firma ASCII NSO0. La cabecera describe segmentos, tamaños, flags y otros metadatos necesarios para localizar y cargar el contenido.

Un título puede contener más de un módulo, como main, rtld o módulos auxiliares con nombres del tipo subsdk. El nombre por sí solo no garantiza que dos archivos cumplan el mismo papel entre juegos o versiones. Identifica cada módulo por su ruta, su cabecera y el contexto del paquete que lo contiene.

Un NSO no es el paquete completo del juego

El módulo es solo una parte del software instalado. Los recursos y otros archivos ejecutables pueden vivir en contenedores o particiones distintos. Inspecciona únicamente copias de archivos que tengas derecho a utilizar.

2. Mapa de la cabecera

Campos principales de la cabecera NSO
Offset de cabecera Campo Descripción general
0x00 Magic Firma NSO0.
0x04 Versión Campo de versión del formato.
0x0C Flags Bits que describen opciones del módulo, incluidas condiciones de compresión.
0x10 Descriptor de .text Información de ubicación, dirección de memoria y tamaño descomprimido.
0x20 Descriptor de .rodata Información equivalente para datos de solo lectura.
0x30 Descriptor de .data Información equivalente para datos modificables.
0x40 Build ID Identificador de 32 bytes asociado al módulo.

Los offsets de esta tabla son posiciones dentro de la cabecera, no offsets de los segmentos en el archivo. Cada descriptor reúne campos distintos; interpreta sus miembros según la especificación NSO y no como un único número grande. La cabecera también contiene otros metadatos, por lo que este resumen no sustituye un parser completo.

3. Segmentos y direcciones

Los segmentos principales separan código, datos de solo lectura y datos que el programa puede modificar. Cada descriptor permite relacionar la representación almacenada en el archivo con la representación que utiliza el proceso al ejecutarse.

Conceptos que aparecen en los descriptores de segmento
Concepto Pregunta No confundir con
Offset de archivo ¿Dónde están los bytes almacenados en el NSO? Una dirección virtual del proceso.
Offset de memoria ¿En qué posición relativa se mapea el segmento? Un offset del archivo completo.
Tamaño descomprimido ¿Cuántos bytes ocupa el segmento una vez preparado? La longitud comprimida que ocupa en el NSO.
Tamaño comprimido ¿Cuántos bytes se almacenaron si el segmento está comprimido? El tamaño lógico en memoria.
BSS ¿Qué espacio se reserva y se inicializa en memoria? Datos que necesariamente aparecen como bytes en el archivo.

Las direcciones de memoria del proceso no se convierten a offsets del archivo mediante una resta universal. Primero se identifica el módulo, el segmento y su dirección de mapeo; luego se comprueba que la dirección esté dentro del rango de ese segmento. El BSS merece atención especial porque puede reservar espacio que no ocupa una secuencia equivalente de bytes en el NSO.

4. Compresión y datos almacenados

Los segmentos NSO pueden almacenarse comprimidos. La cabecera indica condiciones que permiten al cargador o a las herramientas interpretar los bytes. Por eso, una búsqueda directa de instrucciones sobre el archivo comprimido puede no encontrar el patrón esperado.

  • Flags: describen propiedades del módulo y qué segmentos tienen una representación comprimida.
  • Offset: señala dónde comienza la representación del segmento en el archivo NSO.
  • Tamaño comprimido: describe el rango almacenado cuando aplica al formato.
  • Tamaño lógico: permite comprobar la longitud tras la descompresión.
  • Integridad: ciertos campos auxiliares pueden permitir validar el contenido descomprimido.

LZ4 es una compresión frecuente en este contexto, pero no deduzcas el algoritmo solo porque los bytes parezcan comprimidos. Usa una herramienta que reconozca NSO y sus flags. Extraer bytes de un rango y pasarlos a un descompresor genérico sin conocer los límites puede producir errores o una salida engañosa.

No edites el segmento comprimido como si fuera código plano

Para inspeccionar instrucciones, trabaja con una copia descomprimida que conserve su relación con el módulo original. Si un flujo posterior requiere volver a crear el NSO, el segmento debe recomprimirse y los metadatos relacionados deben actualizarse correctamente.

5. Por qué importa el Build ID

El Build ID es un identificador de 32 bytes asociado a un módulo ejecutable concreto. Las herramientas de modificación lo usan para distinguir compilaciones y comprobar si un conjunto de cambios está destinado al módulo que se inspecciona.

Una actualización puede cambiar código, datos, disposición de segmentos o decisiones del compilador. Como consecuencia, una modificación basada en posiciones de una compilación anterior puede dejar de corresponder a las instrucciones o estructuras esperadas. El Build ID ayuda a detectar esa diferencia antes de aplicar cambios.

Conexión con los parches

Como vimos en Parches de código, ciertos flujos de parches asocian archivos con el Build ID del módulo que esperan modificar. La asociación identifica el destino; no demuestra por sí sola que el contenido del parche sea correcto o seguro.

6. Leer y registrar el Build ID

El Build ID se representa como 32 bytes. Una herramienta puede mostrarlo como una cadena hexadecimal continua, con separadores o en grupos. Conserva el valor tal como lo presenta el parser y registra el módulo del que procede: un identificador sin nombre de archivo no basta para una comparación reproducible.

7. Versiones y módulos distintos

El Build ID pertenece al módulo, no es un identificador universal de todo el título. Dos módulos de la misma instalación pueden tener IDs diferentes. Del mismo modo, la etiqueta visible de una versión del juego no siempre permite deducir todos los IDs de sus módulos.

  • Compara el ID del mismo módulo con el ID esperado por la herramienta o el parche.
  • No asumas que main y un subsdk comparten el identificador.
  • Una actualización puede reemplazar uno o varios módulos, no necesariamente todos.
  • El nombre del archivo puede repetirse en distribuciones distintas; registra también el origen y la revisión.

Si un paquete contiene varios ejecutables, crea un inventario con una fila por archivo. Esto evita aplicar accidentalmente a un módulo una referencia que solo era válida para otro.

8. Flujo de inspección

Una inspección ordenada comienza identificando el archivo y termina guardando un registro que permita repetir el análisis. No es necesario modificar el módulo para leer su cabecera y comprobar su Build ID.

  1. Conserva el original: trabaja sobre una copia y anota tamaño y procedencia.
  2. Identifica el formato: comprueba que el archivo comienza con una firma NSO válida.
  3. Lee la cabecera: revisa versión, flags y descriptores de segmentos.
  4. Registra el Build ID: conserva los 32 bytes y el nombre del módulo.
  5. Valida segmentos: comprueba que offsets y tamaños no excedan el archivo.
  6. Descomprime solo si hace falta: usa un parser compatible con las flags y conserva la salida aparte.
  7. Compara con la referencia: confirma que el identificador esperado corresponda a ese módulo.

9. Compatibilidad de parches

Un Build ID coincidente es una condición de selección, no una prueba completa de compatibilidad. Verifica además qué módulo espera el parche, qué método de aplicación utiliza y si sus offsets se expresan respecto al archivo almacenado o al segmento cargado.

Preguntas antes de usar un parche de módulo
Pregunta Por qué importa
¿Coincide el módulo objetivo? Un ID de otro ejecutable no describe el destino correcto.
¿Coincide el Build ID completo? Un parche puede depender de una compilación exacta.
¿Qué espacio de offsets usa? Offsets de archivo y offsets de memoria pueden ser distintos.
¿La herramienta valida el destino? Reduce el riesgo de modificar bytes que no corresponden.
¿Existe copia de respaldo y método de reversión? Permite recuperar el estado anterior si el resultado falla.

No fuerces un parche ignorando un ID distinto ni renombres un archivo para que parezca compatible. Si el ID cambió, busca una versión del parche dirigida al módulo exacto o vuelve a analizar el módulo de forma independiente.

10. Diagnóstico de problemas

Problemas habituales al identificar un NSO
Síntoma Causa posible Comprobación
No aparece la firma NSO0 El archivo no es NSO, está envuelto en otro contenedor o el offset no es el inicio. Confirma el archivo y la herramienta de extracción.
Los bytes del segmento no parecen código Segmento comprimido o lectura desde un offset incorrecto. Consulta flags y descriptores con un parser NSO.
El Build ID no coincide con la referencia Revisión, región o módulo distinto. Compara ruta, origen y los 32 bytes completos.
El offset indicado excede el archivo Cabecera inválida, formato mal interpretado o archivo truncado. Valida los límites antes de extraer rangos.
El módulo funciona distinto tras modificarlo Metadatos o segmentos no se reconstruyeron correctamente. Vuelve a una copia limpia y verifica el proceso con herramientas compatibles.

11. Práctica y lista de comprobación

Usa un archivo NSO que tengas derecho a inspeccionar y limita el ejercicio a leer metadatos:

  1. Comprueba si los primeros cuatro bytes corresponden a NSO0.
  2. Anota los offsets de cabecera de los descriptores de .text, .rodata y .data.
  3. Registra el Build ID completo y el nombre o ruta del módulo.
  4. Confirma que los rangos descritos por la cabecera no excedan el tamaño del archivo.
  5. Explica por qué el Build ID no identifica por sí solo toda la versión del título.
Antes de dar por válido el análisis
  • ¿La firma y el tipo de archivo se confirmaron?
  • ¿Separé offsets de archivo y direcciones de memoria?
  • ¿Interpreté flags y tamaños con una herramienta compatible?
  • ¿Registré el Build ID completo junto al módulo correspondiente?
  • ¿Validé que los segmentos y sus tamaños caben en el archivo?
  • ¿Conservé intacta la copia original?
