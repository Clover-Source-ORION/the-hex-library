Hexadecimal y little endian en DS

Antes de analizar archivos de Nintendo DS conviene dominar la lectura hexadecimal y distinguir cómo se representan los valores de varios bytes. Esta guía recorre bytes, endianness y direcciones con ejemplos para que puedas inspeccionar una ROM sin confundir posiciones del archivo con direcciones de memoria.

1. Un byte, dos dígitos

Un byte contiene ocho bits y puede representar un valor sin signo entre 0 y 255. En hexadecimal se escribe con dos dígitos, desde 0x00 hasta 0xFF. Cada dígito hexadecimal representa cuatro bits, también llamados nibble; por ejemplo, 0xA7 equivale a 1010 0111 en binario.

El prefijo 0x indica que el número está expresado en base 16. No forma parte de los bytes almacenados. En un volcado, la secuencia A7 03 son dos bytes consecutivos: 0xA7 seguido por 0x03.

Equivalencias útiles entre bases
Decimal Hexadecimal Binario Uso como byte
0 0x00 0000 0000 Todos los bits apagados.
10 0x0A 0000 1010 Bits 1 y 3 activados.
127 0x7F 0111 1111 Mayor entero con signo de 8 bits.
255 0xFF 1111 1111 Mayor entero sin signo de 8 bits.

2. Little endian: el truco del revés

Los procesadores ARM de la Nintendo DS usan habitualmente el orden little-endian para los valores multibyte: el byte menos significativo se almacena primero. Para reconstruir el número, se lee la secuencia de bytes desde el último hacia el primero. El orden de los bits dentro de cada byte no cambia.

endian.txtHEX
78 56 34 12   // en el archivo
0x12345678    // valor numérico de 32 bits

34 12         // en el archivo
0x1234        // valor numérico de 16 bits

La palabra «real» puede resultar engañosa: el volcado siempre contiene los bytes en el orden que muestra el editor. Little-endian es una regla para interpretar varios bytes como un solo número; no significa que debas invertir el archivo ni que el contenido textual tenga que leerse al revés.

3. De dirección de RAM a offset

Un offset es una posición contada desde el comienzo de un archivo. Una dirección de RAM es una ubicación del espacio de memoria que el procesador usa al ejecutar el programa. Para convertir entre ambas hace falta saber qué región del archivo se carga en qué dirección; no existe una resta universal que sirva para cualquier parte de una ROM.

Offset del archivo y direcciones de memoria
Valor Tipo Interpretación
0x000000 Offset Primer byte del archivo .nds.
0x02000000 Dirección de memoria Inicio de la WRAM principal en el mapa de memoria DS.
0x02380000 Dirección de memoria Ejemplo de dirección de carga común para una región ARM9; debe confirmarse en la cabecera.
Fórmula para una región cargada

Offset relativo al binario = dirección de RAM − dirección de carga del binario. Para obtener un offset del archivo .nds, también hay que sumar el offset de origen del binario dentro de la ROM. Ambos datos se leen de la cabecera y describen regiones concretas.

Por ejemplo, si la cabecera indica que arm9.bin empieza en el archivo en 0x4000 y se carga en RAM en 0x02000000, la dirección 0x02000120 corresponde al offset 0x120 dentro del binario y al offset 0x4120 en la ROM. Esta relación solo aplica a bytes que pertenecen a esa región cargada.

4. Bits, nibbles y conversiones

Hexadecimal es cómodo porque cada dígito corresponde exactamente a cuatro bits. Para inspeccionar flags o campos empaquetados, conviene escribir el byte en binario y numerar las posiciones desde cero, empezando por el bit menos significativo.

bits_y_nibbles.txtBINARIO
Hex:      0xA7
Binario:  1010 0111
Nibble:   A    7

Bit:      7 6 5 4 3 2 1 0
Valor:    1 0 1 0 0 1 1 1

El valor de un nibble puede extraerse con una máscara. El nibble bajo conserva los bits 0 a 3; el nibble alto conserva los bits 4 a 7. Para interpretar los bits como banderas, primero consulta la estructura del formato: no asumas que todos representan opciones independientes.

mascaras.txtOPERACIONES
byte = 0xA7
nibble_bajo = byte & 0x0F       // 0x07
nibble_alto = (byte >> 4) & 0x0F // 0x0A

bit_2 = (byte >> 2) & 1         // 1

5. Tamaños, signo y valores

Antes de interpretar una secuencia, determina cuántos bytes ocupa el campo. El mismo patrón de bits puede significar distintos números según se lea como entero de 8, 16 o 32 bits, y según sea con signo o sin signo.

Rangos de enteros comunes
Ancho Sin signo Con signo Bytes
8 bits 0 a 255 -128 a 127 1
16 bits 0 a 65 535 -32 768 a 32 767 2
32 bits 0 a 4 294 967 295 -2 147 483 648 a 2 147 483 647 4

En complemento a dos, el bit más alto distingue la mitad negativa del rango con signo. Por ejemplo, el byte FF puede ser 255 sin signo o -1 con signo. Los bytes no indican por sí mismos cuál interpretación es la correcta; el programa que los consume y el formato de datos determinan el tipo.

6. Leer un volcado hexadecimal

Un editor suele mostrar el offset de cada fila, los bytes en hexadecimal y una columna de texto aproximada. La columna ASCII ayuda a localizar cadenas, pero los valores fuera del rango imprimible se muestran como puntos u otros símbolos y no son necesariamente errores.

volcado_ejemplo.txtHEX DUMP
Offset      Bytes                                      Texto
00001000    48 45 4C 4C 4F 00 20 00 78 56 34 12       HELLO. .xV4.
0000100C    FF 7F 00 00 02 00 00 00 41 42 43 44       ........ABCD

0x1000 a 0x1004   Texto ASCII: "HELLO"
0x1005             Terminador cero
0x1008 a 0x100B   Entero LE de 32 bits: 0x12345678

Los offsets de la columna izquierda suelen señalar el primer byte de la fila. Si una fila contiene 16 bytes, la siguiente dirección aumenta en 0x10. Antes de copiar bytes de una captura, confirma el offset inicial y el número de bytes seleccionados.

7. Alineación y límites

Algunas estructuras colocan campos en fronteras específicas, por ejemplo, una palabra de 32 bits en un offset múltiplo de cuatro. La alineación es una convención de la estructura o del código que accede a ella; no es una regla que permita concluir por sí sola que cualquier posición desalineada sea incorrecta.

  • Byte: puede comenzar en cualquier offset.
  • Halfword de 16 bits: a menudo se alinea a 2 bytes.
  • Word de 32 bits: a menudo se alinea a 4 bytes.
  • Bloque empaquetado: puede no estar alineado como un entero nativo; interpreta según su formato.

Los límites también importan: para leer un valor de cuatro bytes desde el offset n, deben existir los bytes n, n+1, n+2 y n+3. Una lectura que termina un byte después del archivo es un error, aunque el valor parcialmente leído parezca plausible.

8. Archivo NDS y mapa de memoria

Una ROM de DS contiene una cabecera y regiones como el ejecutable ARM9, el ejecutable ARM7 y el sistema de archivos NitroFS. Los offsets de esas regiones pertenecen al archivo; las direcciones de carga y los puntos de entrada pertenecen al mapa de memoria. La cabecera proporciona los pares necesarios para relacionar las regiones ejecutables.

Campos que conviene separar al analizar una ROM
Campo Espacio Pregunta que responde
Offset del ejecutable en ROM Archivo ¿Dónde comienzan sus bytes en el archivo?
Dirección de carga Memoria ¿Dónde se copia el ejecutable para correr?
Tamaño del ejecutable Bytes ¿Qué rango se copia o procesa?
Punto de entrada Memoria ¿En qué dirección comienza la ejecución?
Offset de un archivo NitroFS Archivo/contenedor ¿Dónde comienza ese archivo dentro de la ROM?

Un archivo almacenado en NitroFS no tiene por qué cargarse en la dirección que usa el ejecutable ARM9. El juego puede leerlo, descomprimirlo y copiarlo a una región de RAM diferente. No apliques la fórmula de una región ejecutable a recursos del sistema de archivos sin evidencia de que comparten ese mapeo.

9. Ejemplo con ARM9

Supongamos que los campos de la cabecera de una ROM indican que el binario ARM9 comienza en el offset 0x4000 y se carga en 0x02000000. Si una dirección de una referencia cae en 0x02000120, podemos calcular su posición relativa dentro del binario y su posición dentro de la ROM.

conversion_arm9.txtEJEMPLO
Offset ARM9 en ROM:       0x00004000
Dirección de carga ARM9:  0x02000000
Dirección a investigar:   0x02000120

Offset dentro de ARM9:
0x02000120 - 0x02000000 = 0x00000120

Offset equivalente en ROM:
0x00004000 + 0x00000120 = 0x00004120

Antes de aceptar el resultado, verifica que la dirección esté dentro del rango de carga ARM9 descrito por la cabecera. La fórmula no convierte direcciones de otras regiones, direcciones de RAM dinámica ni datos que el juego haya copiado a una ubicación diferente.

10. Lectura con herramientas y Python

Los editores hexadecimales permiten inspeccionar bytes sin alterar el archivo. Para automatizar lecturas, especifica siempre el endianness y comprueba que la cantidad solicitada se haya leído completa.

leer_enteros.pyPYTHON 3
import struct
from pathlib import Path

rom = Path("juego.nds").read_bytes()
offset = 0x1000

if offset + 4 > len(rom):
    raise ValueError("No hay cuatro bytes disponibles en ese offset")

valor_le = struct.unpack_from("<I", rom, offset)[0]
valor_be = struct.unpack_from(">I", rom, offset)[0]

print(f"Little-endian: 0x{valor_le:08X}")
print(f"Big-endian:    0x{valor_be:08X}")

El prefijo < solicita little-endian y > big-endian; I indica un entero sin signo de 32 bits. Para un campo de 16 bits se usa H, y para un byte individual se puede indexar directamente el arreglo de bytes. Selecciona el tipo que indique la estructura analizada.

tabla_de_tamanos.txtPYTHON STRUCT
"<B"  // 1 byte sin signo
"<H"  // 2 bytes sin signo little-endian
"<I"  // 4 bytes sin signo little-endian
"<i"  // 4 bytes con signo little-endian

11. Errores frecuentes

Problemas típicos al interpretar datos
Síntoma Posible causa Qué verificar
Un valor parece enorme Se interpretó little-endian como big-endian o se usó el ancho equivocado. Revisa orden de bytes, cantidad de bytes y signo.
La dirección calculada no coincide con el archivo Se aplicó la dirección de carga a un offset de NitroFS. Identifica primero qué región contiene los datos.
Los bytes en el editor no coinciden con el valor escrito Se invirtieron todos los bits o se invirtieron bytes dos veces. Escribe el valor en bytes y contrástalo con un ejemplo conocido.
La lectura termina con menos datos de los esperados Offset cercano al final del archivo o tamaño incorrecto. Comprueba el límite antes de leer.
Un campo negativo aparece positivo Se decodificó un entero con signo como no signado. Consulta la estructura y el tipo usado por el programa.
Una cadena muestra puntos en el volcado Los bytes no son caracteres ASCII imprimibles. Puede ser un campo binario; no lo conviertas en texto a la fuerza.

12. Práctica y lista de comprobación

Prueba estas conversiones con papel, calculadora hexadecimal o un pequeño script:

  1. Interpreta 34 12 como entero little-endian de 16 bits.
  2. Escribe 0x12345678 como cuatro bytes little-endian.
  3. Indica los nibbles alto y bajo de 0xA7.
  4. Si el ARM9 comienza en el archivo en 0x4000 y se carga en 0x02000000, convierte 0x02000080 a offset de ROM.
  5. Explica por qué una dirección de RAM no puede convertirse en un offset de NitroFS con la misma fórmula sin más información.
Antes de anotar un valor
  • ¿Conozco el offset inicial y el ancho del campo?
  • ¿Sé si el entero es little-endian, big-endian o un campo empaquetado?
  • ¿Sé si el valor es con signo, sin signo, dirección o tamaño?
  • ¿Estoy trabajando con un offset de archivo o una dirección de memoria?
  • ¿La región y el límite de lectura están confirmados?
