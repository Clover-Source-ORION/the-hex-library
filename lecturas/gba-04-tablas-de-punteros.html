Tablas de punteros

Una tabla de punteros se parece al índice de un libro: no contiene los recursos, sino referencias que indican dónde encontrarlos. En esta lectura aprenderás a distinguir direcciones de offsets, reconocer patrones sin confiar en una sola pista y validar cada cambio antes de probarlo en el juego.

1. ¿Qué es un puntero?

Un puntero es un valor que identifica la ubicación de otro dato. En muchos juegos de GBA, las referencias a recursos de ROM se almacenan como palabras de 32 bits; el procesador usa una dirección de su mapa de memoria, mientras que el editor hexadecimal muestra un offset dentro del archivo. Son dos formas de nombrar ubicaciones diferentes.

La ROM suele ser visible desde la ventana que comienza en 0x08000000. Por eso es frecuente encontrar palabras como 0x083B4E80. No todos los juegos almacenan direcciones absolutas ni toda palabra que empiece por 08 es automáticamente un puntero: hay que confirmar el formato y el contexto.

ejemplo_puntero.hexHEX
// bytes en la ROM
80 4E 3B 08

// valor numérico Little-Endian: 0x083B4E80
// offset para la ventana 0x08: 0x083B4E80 - 0x08000000
// resultado: 0x003B4E80

2. Direcciones y offsets

Para un puntero directo a la ventana que empieza en 0x08000000, la conversión habitual es sumar o restar esa base. La máscara puede ser una abreviatura, pero solo debe usarse cuando ya sabes que el puntero pertenece a esa ventana y el offset cabe en el archivo.

  • Offset a dirección: dirección = 0x08000000 + offset.
  • Dirección a offset: offset = dirección - 0x08000000.
  • Ejemplo: 0x08000000 + 0x003B4E80 = 0x083B4E80.
No conviertas a ciegas

La operación puntero & 0x01FFFFFF solo obtiene los bits inferiores. No comprueba que el puntero esté en la ventana correcta ni que el destino exista. Una conversión aparentemente razonable todavía puede apuntar fuera del archivo.

3. Little-Endian en el editor hexadecimal

Los valores multibyte de GBA suelen almacenarse en Little-Endian: el byte menos significativo aparece primero en el archivo. Para reconstruir el número, el orden de lectura de los bytes se invierte; no se invierten los bits que hay dentro de cada byte.

La palabra 0x083B4E80 se divide en los bytes 08, 3B, 4E y 80. En el archivo se ven en el orden contrario: 80 4E 3B 08. Cuando escribas una dirección nueva, codifícala también en Little-Endian.

codificar_puntero.txtHEX
Dirección: 0x08123456
Bytes:     56 34 12 08

Dirección: 0x08002000
Bytes:     00 20 00 08

4. Cómo reconocer una tabla

Una tabla de punteros suele ser una serie de entradas contiguas que comparten un formato. Las siguientes señales ayudan a encontrar candidatas, pero ninguna basta por sí sola para confirmar que una región sea una tabla:

  • Valores válidos: al convertirlos con la regla correcta, varios apuntan dentro del archivo.
  • Repetición: las entradas aparecen con un ancho regular, por ejemplo cada 4 bytes.
  • Destinos coherentes: los offsets resultantes caen al inicio de textos, gráficos u otras estructuras reconocibles.
  • Referencias de código: una rutina lee las entradas con el tamaño y el formato que propones.

Una serie creciente es común cuando los recursos se almacenaron uno tras otro, pero no es un requisito. También puede haber destinos repetidos, datos compartidos, orden distinto al de la tabla o recursos repartidos en varias zonas.

candidata_a_tabla.hexHEX
00A10000: 10 20 3B 08  4C 20 3B 08  88 20 3B 08

// Valores interpretados: 0x083B2010, 0x083B204C, 0x083B2088
// Offsets:               0x003B2010, 0x003B204C, 0x003B2088
// Diferencias:           0x3C y 0x3C (pista, no prueba)

En el ejemplo, la separación de 0x3C puede corresponder al tamaño de recursos de longitud fija, a una alineación o a una coincidencia. Inspecciona los destinos y busca más entradas antes de concluir que cada dato mide exactamente 60 bytes.

5. Entradas y estructuras repetidas

Una tabla también puede apuntar a registros de tamaño fijo. En ese caso, cada registro contiene varios campos y solo algunos son punteros. Una separación regular entre registros no significa que todos sus campos sean direcciones.

registro_objeto.cESTRUCTURA
struct Objeto {
    uint16_t id;
    uint16_t precio;
    uint32_t puntero_nombre;
    uint32_t puntero_descripcion;
};

// Tamaño ilustrativo: 12 bytes, si el compilador no inserta padding.
// Los dos punteros están en +0x04 y +0x08.

En una ROM no hay nombres de campos ni tipos. Para reconstruir un registro, registra los offsets relativos de cada posible campo, comprueba si el patrón se repite y valida cada supuesto por separado. Un número pequeño que varía poco puede ser un identificador o una longitud, no un puntero.

  • Ancho: confirma si el campo ocupa 2, 3 o 4 bytes.
  • Stride: mide la distancia entre el inicio de registros consecutivos.
  • Campos: anota qué posiciones parecen direcciones y cuáles podrían ser atributos.
  • Destino: prueba cada campo con una conversión independiente y comprueba el contenido.

6. Búsqueda inversa

La búsqueda inversa parte de un recurso cuya ubicación ya conoces y busca qué bytes podrían referenciarlo. Calcula la dirección candidata usando el formato confirmado, conviértela a Little-Endian y busca esa secuencia en el archivo. Anota todas las coincidencias: una puede ser una referencia real y otras pueden aparecer por casualidad dentro de datos.

buscar_referencias.pyPYTHON 3
import struct
from pathlib import Path

def buscar_referencias(rom_path, offset_destino):
    rom = Path(rom_path).read_bytes()
    if not 0 <= offset_destino < len(rom):
        raise ValueError("El destino debe estar dentro de la ROM")
    if offset_destino >= 0x02000000:
        raise ValueError("El ejemplo solo admite la ventana 0x08")

    direccion = 0x08000000 + offset_destino
    patron = struct.pack("<I", direccion)
    resultados = []
    inicio = 0

    while True:
        posicion = rom.find(patron, inicio)
        if posicion == -1:
            break
        resultados.append(posicion)
        inicio = posicion + 1

    return resultados

for posicion in buscar_referencias("juego.gba", 0x003B4E80):
    print(f"Posible referencia en ROM+0x{posicion:06X}")

Este programa solo busca palabras absolutas en la ventana 0x08; no detecta offsets relativos, entradas comprimidas ni punteros de otro tamaño. Cada resultado requiere contexto. Examina la zona que lo rodea y comprueba si el código o una estructura repetida realmente consume esa palabra como referencia.

7. Formatos distintos de puntero absoluto

Si las direcciones aparentes no encajan, puede que el motor guarde otra representación. Busca evidencia en las instrucciones que leen la tabla o en una rutina conocida antes de aplicar una conversión distinta.

  • Offset relativo: se suma a una base común o a la ubicación de la propia entrada.
  • Dirección empaquetada: ciertos bits pueden indicar un tipo, un banco o flags.
  • Valor de 16 o 24 bits: puede ser un offset reducido o un índice dentro de otra tabla.
  • Sentinela: valores como 0x00000000 o 0xFFFFFFFF pueden significar «sin dato».
  • Referencia comprimida: el dato puede requerir descompresión y tener una longitud almacenada aparte.
Primero observa, después interpreta

Que un valor pueda convertirse en un offset dentro del archivo no prueba que sea un puntero. Verifica cómo se calcula el destino y qué hace el programa cuando encuentra valores especiales.

8. Reubicación con control

Cuando un recurso nuevo ocupa más espacio, puede ser necesario moverlo y actualizar las referencias. No basta con encontrar una secuencia de FF: podría ser relleno usado por otra estructura o formar parte de un bloque comprimido. Sigue un proceso reversible y conserva siempre el archivo original.

  1. Duplica la ROM: trabaja sobre una copia y guarda una copia limpia sin modificar.
  2. Determina los límites: conoce el principio, la longitud y cualquier terminador o cabecera del recurso.
  3. Confirma el espacio: revisa que el rango de destino no esté ocupado ni reservado.
  4. Respeta las restricciones: considera alineación, tamaño máximo de ROM y rango del formato de puntero.
  5. Escribe el recurso completo: incluye cabeceras, tamaños y datos auxiliares si el motor los requiere.
  6. Actualiza referencias: identifica si hay más de una entrada o una tabla duplicada.
  7. Comprueba el cambio: vuelve a leer los bytes escritos antes de abrir el juego.

Si el puntero es absoluto de la ventana 0x08, un destino situado en el offset 0x00400000 se codifica como la dirección 0x08400000, es decir, los bytes 00 00 40 08. Calcula el valor con una herramienta o una operación explícita; evita escribirlo de memoria.

Las referencias antiguas también cuentan

Un mismo recurso puede estar referenciado desde más de una tabla o desde código directo. Actualizar solo una coincidencia puede dejar el juego en un estado inconsistente. Revisa cada referencia y prueba todas las pantallas o acciones que usan ese dato.

9. Verificación y errores comunes

Diagnóstico inicial de problemas con punteros
Síntoma Posible causa Comprobación
El destino cae fuera del archivo Endian incorrecto, base equivocada o formato distinto. Decodifica bytes y confirma la ventana antes de convertir.
Se ve parte del recurso equivocado Offset apunta al interior de un bloque o la longitud se calculó mal. Inspecciona cabeceras, terminadores y límites del recurso.
Un cambio no aparece en el juego Se modificó una copia secundaria o la ruta usa otra tabla. Busca todas las referencias y sigue el flujo de uso.
El juego se bloquea después del cambio Puntero inválido, datos truncados o metadatos omitidos. Compara bytes, longitud, compresión y checksum si aplica.
La tabla parece válida pero apunta a basura Coincidencia accidental o interpretación errónea del formato. Verifica varias entradas y busca la rutina que las consume.

Haz las comprobaciones en orden: confirma el valor hexadecimal, conviértelo, valida el rango del archivo y analiza el contenido en el destino. Solo entonces prueba el juego. Cambiar varias cosas a la vez dificulta saber cuál produjo el fallo.

10. Práctica y lista de comprobación

Usa estos ejemplos para practicar con una ROM de prueba o con datos inventados; no cambies el volcado original.

  1. Convierte 0x083B4E80 a offset suponiendo que pertenece a la ventana 0x08.
  2. Escribe en Little-Endian la dirección 0x08123456.
  3. Explica por qué una coincidencia aislada de cuatro bytes no confirma una referencia.
  4. Si dos recursos tienen direcciones separadas por 0x40, enumera dos razones por las que eso no demuestra que el primero mida 64 bytes.
  5. Busca una entrada cuyo destino conozcas y compara el contexto de la coincidencia con otras entradas candidatas.
Antes de guardar una modificación
  • ¿La ROM de trabajo es una copia y el original permanece intacto?
  • ¿Se conoce el tamaño, el endianness y el formato de cada entrada?
  • ¿El destino convertido cae dentro del archivo y señala datos coherentes?
  • ¿Se revisaron las referencias adicionales y los valores especiales?
  • ¿Se comprobó el recurso extraído y se probó la ruta afectada en el juego?
