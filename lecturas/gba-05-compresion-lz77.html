GBA

Compresión LZ77

Los cartuchos tenían espacio limitado, así que muchos gráficos, mapas y otros recursos se guardan comprimidos. LZ77 aprovecha las repeticiones: en vez de escribir de nuevo una secuencia que ya apareció, almacena una referencia a los bytes anteriores. Esta lectura explica el formato usado por la BIOS de GBA y cómo inspeccionarlo sin perder de vista sus límites.

1. La cabecera de 4 bytes

Un bloque comprimido con el formato LZ77 de la BIOS empieza con una cabecera de cuatro bytes. El primer byte identifica el tipo de compresión; los tres siguientes almacenan el tamaño esperado de salida en orden little-endian. Ese tamaño corresponde a los datos ya descomprimidos, no al número de bytes que ocupa el bloque en la ROM.

Cabecera LZ77
Byte Ejemplo Significado
0 10 Identificador del formato LZ77 de BIOS.
1 0C Byte menos significativo del tamaño descomprimido.
2 00 Byte intermedio del tamaño descomprimido.
3 00 Byte más significativo del tamaño descomprimido.

En el ejemplo, 0C 00 00 se interpreta como 0x00000C, es decir, 12 bytes de salida. El tamaño ocupa 24 bits y se almacena como un entero, no como una dirección. En una herramienta de lectura, calcula el valor explícitamente para evitar invertir el orden de los bytes.

leer_cabecera.txtHEX
10 0C 00 00
│  └─────┘
│   tamaño descomprimido: 0x00000C = 12 bytes
└──── tipo de bloque: LZ77 BIOS
El tamaño no indica dónde termina el bloque comprimido

La cabecera informa cuántos bytes producir. No proporciona directamente el tamaño total comprimido. Para encontrar el siguiente recurso, hay que decodificar hasta alcanzar la salida esperada o conocer la longitud por otra estructura.

2. Banderas y referencias

Después de la cabecera, cada grupo comienza con un byte de banderas que describe hasta ocho elementos siguientes. Los bits se consumen del más significativo al menos significativo: bit 7, bit 6 y así sucesivamente hasta bit 0.

Interpretación de un grupo de banderas
Bit Valor Elemento siguiente Bytes consumidos
7 0 Literal: copiar el byte tal cual. 1
6 1 Referencia a datos anteriores. 2
5 a 0 Se repite el mismo criterio Un bit describe cada elemento en orden. 1 o 2 por elemento

Un bit a 0 indica un literal, es decir, un byte que se copia directamente a la salida. Un bit a 1 indica una referencia de dos bytes. La referencia codifica longitud y distancia en una palabra de 16 bits, con el byte más significativo primero dentro del par.

referencia_lz77.txtFORMATO
Primer byte:  LLLL DDDD
Segundo byte: DDDD DDDD

longitud  = L + 3
distancia = D + 1

L = nibble alto del primer byte
D = 12 bits inferiores formados por el nibble bajo
    del primer byte y el segundo byte

La longitud representable por una referencia va de 3 a 18 bytes. La distancia representable va de 1 a 4096 bytes hacia atrás. La distancia se mide desde la posición actual de salida; no es un offset absoluto dentro de la ROM ni dentro del bloque comprimido.

3. Un ejemplo real

En el bloque siguiente, el primer byte de banderas es 0x10, que en binario es 00010000. Por lo tanto, los tres primeros elementos son literales y el cuarto es una referencia. Los bits restantes no se usan porque la salida ya alcanza los 12 bytes indicados por la cabecera.

lz77.hexHEX
10 0C 00 00  // LZ77, 12 bytes de salida
10           // banderas 0001 0000: 3 literales y 1 referencia
41 42 43     // "ABC"
60 02        // copia 9 bytes desde 3 atrás
// resultado: ABCABCABCABC

El par 60 02 representa la palabra 0x6002. El nibble alto es 6, así que la longitud es 6 + 3 = 9. Los doce bits restantes valen 0x002, por lo que la distancia es 2 + 1 = 3.

Salida del ejemplo, byte a byte
Paso Acción Salida acumulada Tamaño
1 Literal 41 = A A 1
2 Literal 42 = B AB 2
3 Literal 43 = C ABC 3
4 a 12 Copiar longitud 9, distancia 3 ABCABCABCABC 12
Dato curioso

La copia puede solaparse con lo que se está escribiendo. Después de emitir ABC, el decodificador copia desde tres bytes atrás. Los bytes recién producidos pasan a formar parte de la misma ventana, así que nueve bytes salen de solo tres literales.

4. La ventana de búsqueda

El decodificador mantiene como referencia los bytes que ya produjo. Una distancia de 1 repite el último byte; una distancia de 3 vuelve tres posiciones desde el final de la salida disponible. La referencia debe apuntar a una posición ya escrita.

En el ejemplo, al comienzo de la referencia la salida es A B C. La distancia 3 localiza la A. Cada byte se copia uno por uno y la salida se amplía durante la operación:

copia_solapada.txtSECUENCIA
Inicio:       A B C
Copiar 1:     A B C A
Copiar 2:     A B C A B
Copiar 3:     A B C A B C
Copiar 4:     A B C A B C A
Copiar 5:     A B C A B C A B
Copiar 6:     A B C A B C A B C
Copiar 7:     A B C A B C A B C A
Copiar 8:     A B C A B C A B C A B
Copiar 9:     A B C A B C A B C A B C

Una implementación que copie un bloque fijo de memoria de una sola vez puede fallar en referencias solapadas. La forma más clara de evitarlo es leer el byte desde salida[len(salida) - distancia] en cada iteración, añadirlo y volver a calcular la posición con la nueva longitud.

Distancia y longitud son campos distintos

La distancia determina de dónde empieza la copia; la longitud determina cuántos bytes se generan. Una referencia puede copiar más bytes que su distancia, precisamente porque permite el solapamiento.

5. Flujo de descompresión

El proceso se organiza en grupos de hasta ocho elementos. Se lee un byte de banderas, se examina cada bit desde el más alto y se consume un literal o una referencia según corresponda. Se repite hasta alcanzar el tamaño descomprimido declarado en la cabecera.

  1. Lee la cabecera: valida el tipo y obtiene el tamaño final.
  2. Lee banderas: carga un byte y comienza por el bit 7.
  3. Decodifica un elemento: bit cero significa literal; bit uno, referencia de dos bytes.
  4. Actualiza la salida: añade el byte o los bytes copiados.
  5. Comprueba el tamaño: detente al alcanzar la longitud esperada, incluso si quedan bits de banderas.
  6. Comprueba límites: no leas más allá de la entrada ni escribas más allá del tamaño anunciado.

El último grupo puede tener menos de ocho elementos útiles. Los bits sobrantes de ese byte de banderas no implican que haya más recursos ni que deban consumirse. La condición de fin principal es haber generado exactamente la cantidad de bytes indicada por la cabecera.

6. Pseudocódigo del decodificador

El pseudocódigo muestra la lógica central. En una herramienta real, las operaciones de lectura deben comprobar que los bytes solicitados existen y devolver un error claro si el bloque está truncado.

decodificador_lz77.txtPSEUDOCÓDIGO
leer y validar el byte de tipo 0x10
tamaño = leer los siguientes 3 bytes como entero little-endian
salida = secuencia vacía

mientras longitud(salida) < tamaño:
    banderas = leer un byte

    para bit desde 7 hasta 0:
        si longitud(salida) == tamaño:
            terminar

        si el bit está apagado:
            salida.agregar(leer un byte)
        si no:
            primero = leer un byte
            segundo = leer un byte
            longitud = (primero >> 4) + 3
            distancia = (((primero & 0x0F) << 8) | segundo) + 1

            repetir longitud veces:
                salida.agregar(salida[longitud(salida) - distancia])

En la parte final, la longitud de referencia podría llevar la salida más allá del tamaño anunciado si el bloque es inválido. Un decodificador seguro debe rechazar esa entrada o impedir que escriba más bytes de los permitidos, en vez de aceptar una salida silenciosamente distinta.

7. Validaciones y límites

Al analizar un bloque desconocido, comprueba los datos antes y durante la descompresión. Las validaciones evitan lecturas fuera de rango y ayudan a distinguir una cabecera real de una coincidencia accidental.

Comprobaciones mínimas para un decodificador
Dato Validación Si falla
Cabecera Hay al menos 4 bytes y el tipo es el esperado. Tratarlo como bloque desconocido o truncado.
Tamaño de salida Está dentro de un límite razonable definido por la herramienta. Rechazar antes de reservar memoria excesiva.
Datos de entrada Cada lectura de bandera, literal y referencia está dentro del archivo. Informar que el bloque está incompleto.
Distancia No excede la cantidad de bytes ya producidos. La referencia es inválida para el historial disponible.
Longitud La copia no produce más bytes que el tamaño declarado. Detener el análisis y señalar datos inconsistentes.

Un tamaño de salida muy grande puede ser legítimo en ciertos contextos, pero un explorador de ROM debe tener un límite configurable o un límite de seguridad documentado. La cabecera es parte de un archivo no confiable; no conviene reservar memoria ilimitada basándose solo en su valor.

8. Compresión y tamaño

LZ77 es especialmente útil cuando hay patrones repetidos. En imágenes con áreas uniformes, mapas con tiles repetidos o secuencias de datos similares, una referencia puede sustituir muchos bytes por dos. En datos aleatorios, la compresión puede ser pequeña o incluso aumentar el tamaño por las banderas y referencias.

  • Literal: un byte de entrada produce un byte de salida, además del costo amortizado de la bandera.
  • Referencia: dos bytes de entrada producen entre 3 y 18 bytes de salida.
  • Bandera: un byte describe hasta ocho elementos; si el grupo no se llena, algunos bits quedan sin usar.
  • Cabecera: los cuatro bytes indican formato y tamaño descomprimido.

El tamaño descomprimido no permite deducir exactamente el tamaño comprimido. El resultado depende del número de grupos, los literales, las referencias y los bits que quedan sin utilizar en el último grupo. Para localizar el final con precisión, decodifica el flujo y conserva un contador de bytes consumidos.

comparacion_tamano.txtRESUMEN
Datos sin comprimir:   12 bytes
Cabecera LZ77:          4 bytes
Bandera del ejemplo:   1 byte
Literales:             3 bytes
Referencia:            2 bytes
Total de entrada:     10 bytes
Salida generada:      12 bytes

En este ejemplo pequeño se ahorran dos bytes respecto a los 12 bytes originales, sin contar almacenamiento adicional que pueda usar el formato contenedor del juego. En bloques reales, puede haber cabeceras externas, alineación o padding hasta una frontera de 4 bytes.

9. Cómo identificar bloques LZ77

El byte 0x10 es una pista típica, no una confirmación absoluta. Puede aparecer en otro tipo de datos. Para validar una candidata, interpreta el tamaño, ejecuta una descompresión con límites y comprueba si el resultado tiene la estructura esperada para el recurso.

  1. Busca una posible cabecera 10 ?? ?? ?? en una zona donde esperas un recurso.
  2. Decodifica los tres bytes siguientes como tamaño little-endian.
  3. Valida que el tamaño sea razonable y compatible con el tipo de recurso.
  4. Intenta descomprimir respetando límites de entrada, salida y distancia.
  5. Inspecciona la salida con un visor adecuado: texto, mapa, gráfico o estructura.
  6. Compara el resultado con una herramienta independiente cuando sea posible.

Si la salida es un gráfico, un bloque LZ77 correctamente decodificado todavía puede verse irreconocible si se interpreta con el formato de color o el modo de tiles equivocado. La compresión solo reconstruye bytes; no describe por sí misma cómo esos bytes se convierten en píxeles o estructuras del juego.

10. Errores frecuentes

Diagnóstico de problemas al leer LZ77
Síntoma Causa posible Qué revisar
Salida con bytes extraños desde el inicio Offset incorrecto o cabecera que no es LZ77. Confirma el byte de tipo y el comienzo real del bloque.
El decodificador se detiene antes de tiempo El bloque está truncado o las banderas se leen en orden inverso. Revisa límites y procesa los bits desde el 7 hasta el 0.
La salida tiene tamaño equivocado La cabecera se interpretó con endian incorrecto. Combina los bytes 1, 2 y 3 en little-endian.
Las referencias producen un error de historial La distancia es mayor que los bytes ya generados. Comprueba el orden de los dos bytes de referencia y el cálculo de +1.
La salida se repite mal La copia se hizo como bloque no solapado. Copia byte a byte y actualiza la salida en cada paso.
El gráfico sigue sin verse bien La descompresión es correcta, pero el formato visual es otro. Comprueba profundidad, paleta, tiles y dimensiones.

11. Flujo de trabajo recomendado

Separa el análisis del bloque comprimido de la edición del recurso. Conserva los archivos intermedios y apunta cada transformación para poder volver al origen si el resultado cambia inesperadamente.

  1. Guarda el original: trabaja sobre una copia de la ROM y registra su tamaño o hash.
  2. Localiza la referencia: usa una tabla de punteros u otra estructura confirmada para encontrar el inicio del bloque.
  3. Registra la cabecera: anota offset, tipo y tamaño descomprimido.
  4. Extrae y descomprime: conserva el bloque original y la salida en archivos separados.
  5. Inspecciona los bytes: abre la salida con una herramienta acorde al tipo de recurso.
  6. Modifica y recompresa: utiliza el formato que espera el juego y conserva el tamaño o metadatos cuando sea necesario.
  7. Actualiza referencias si hace falta: una salida comprimida más larga puede requerir reubicación.
  8. Prueba el resultado: verifica el recurso en emulador y revisa también los usos relacionados.

La GBA y sus juegos también emplean variantes y formatos propios. Que una herramienta llame a un archivo «LZ77» no garantiza que acepte todas las convenciones del juego. Comprueba el byte de tipo, las particularidades del motor y cómo se carga el recurso.

12. Práctica y lista de comprobación

Practica con el ejemplo de esta página antes de analizar un recurso real:

  1. Convierte 0C 00 00 a tamaño decimal.
  2. Escribe 0x10 en binario e indica qué tres primeros elementos controla.
  3. Decodifica 60 02 y calcula longitud y distancia con las fórmulas.
  4. Explica por qué una referencia de distancia 3 puede generar 9 bytes.
  5. Describe qué debe hacer un lector si el tamaño de cabecera supera el límite de salida permitido.
Lista de comprobación
  • ¿La cabecera tiene cuatro bytes y el identificador de tipo esperado?
  • ¿El tamaño de salida se leyó como entero little-endian de 24 bits?
  • ¿Las banderas se recorren desde el bit más significativo?
  • ¿Se validan los límites antes de cada lectura y escritura?
  • ¿Las referencias permiten solapamiento y verifican la distancia?
  • ¿La salida alcanza exactamente el tamaño declarado?
  • ¿Se distingue la descompresión de la interpretación del recurso?
